# ffew-fightlog — Review of the Product Spec and Technical Plan

Date: 2026-10-26
Reviewed: [product-spec.md](product-spec.md) (v1) and [technical-plan.md](technical-plan.md) (v1), as they stood before any code was written.

## Summary

Both documents are well grounded for a first draft, and the plan's claims about Alliance Auth 5.5 hold up. The problems are elsewhere:

1. Several statements in the spec about what the logs contain are wrong against the actual log corpus.
2. The side-guessing design would place YAGAS on the hostile side with full confidence in the very fight the spec uses for acceptance, and the killmail signals meant to fix that are poisoned by the same smartbomb friendly fire.
3. A handful of pipeline details (neut direction, rebuild coalescing, clock skew, the zKill window) would silently produce wrong numbers.
4. Permissions, merge semantics and several promised table columns are underspecified or not observable from the data.

Recommended changes before M0 are listed at the end.

## 1. What the spec gets wrong against the data

### 1.1 The bracket ticker is the corporation, not the alliance

ESI: corporation 840323545 is **The Forsakened Few**, ticker `FFEW`. Alliance 99011699 is **We Forsakened Few**, ticker `WEFEW`. The spec calls FFEW "alliance 99011699", and both docs treat `[TICK]` as corp-or-alliance (plan §12).

Consequences:

- Logs only ever give corp tickers. Alliance grouping, the "largest enemy group" in the auto title, and alliance-level `FriendlyEntity` matching all need ESI affiliation lookups.
- The plan's ESI operation list (`PostUniverseIds`, `PostCharactersAffiliation`) has no corporation or alliance info calls, so alliance tickers and names cannot be displayed.
- zKill shows about a dozen hostile corporations in the sample fight. Corp-level grouping would fragment the enemy badly.

### 1.2 Solar systems do appear in logs

The spec says "No solar system appears in the log." `(None)` lines record movement in k-space:

```
[ 2026.10.25 21:00:46 ] (None) Undocking from Nema X - Moon 6 - Hedion University to Nema solar system.
[ ... ] (None) Jumping from Jita to Perimeter
```

In the 2026 files, 262 of 2,958 contain `Jumping from` and 169 contain `Undocking from`. Wormhole jumps are **not** logged, and the sample fight was in J-space (zKill: system 31001176), so zKill stays necessary. The log should be the first source and zKill the second.

### 1.3 "Only (combat) lines matter" discards the best friendly-side evidence

The sample's non-combat lines include:

```
(notify) Following Azeroth Uluntil in warp          ×8
(notify) Following Adrianna Utani in warp           ×6
(notify) Following PaidProgramming in warp          ×5
(notify) Regrouping to Adrianna Utani               ×2
(question) PaidProgramming wants you to join their fleet, do you accept?
(question) Are you sure you want to join the fleet commanded by Azeroth Uluntil?
(notify) Disembarking from ship                     ×2
(notify) Starting clone jumping                     ×3
(notify) Your Information Command Burst II has applied bonuses to 2 fleet members.
(notify) External factors are preventing your Multispectrum Shield Hardener II from responding ...
```

Fleet-follow, regroup and fleet-invite lines identify fleet members by name, which is exactly what the side guesser lacks from a single log (§2.1). Reship and clone-jump lines mark engagement boundaries and help track the listener's ship (§3.3). Module names hint at the listener's hull.

### 1.4 The line-format inventory is incomplete

Shapes found in the corpus that neither document mentions:

| Shape | Example (markup stripped) | Note |
|---|---|---|
| Pilot name on rep / tackle / neut actors | `N remote armor repaired by  Thalia  [Razeleao] - Small Remote Armor Repairer II`<br>`Warp scramble attempt from  Sacrilege  [Una Vez] to  Thalia  [Razeleao]` | Depends on the listener's client label setting. `Razeleao`, `Una Vez`, `Tribesmen`, `Dalts` all resolve to characters via ESI. Damage lines in the same file still use `Pilot[TICK](Ship)`. |
| Bare pilot name in damage lines | `N from ThinkBigShiite - Dark Blood Large EMP Smartbomb - Hits` | 2025 logs. `ThinkBigShiite` is a character. |
| Structure target with " - " in the name | `N to JN - The Event Horizon[EVEHD](Astrahus) - Dual 180mm AutoCannon II - Penetrates - Dual 180mm AutoCannon II - Penetrates (N deflected)` | Separator collision, repeated weapon/quality segment, `(N deflected)` suffix. |
| Tackle on the listener | `Warp scramble attempt from Emergent Warden to you!` | So `from Crow to Cenotaph` lines are always third-party. |
| NPC with a player hull name | `N to Orthrus - Quad 800mm Repeating Cannon II - Hits` in a Triglavian site log | Breaks "player hull name ⇒ PvP". |
| Cap transfer | `N remote capacitor transmitted by  Basilisk  - Large Inductive Compact Remote Capacitor Transmitter` | Ship-only actor, as with reps. |
| Nos | `+N GJ energy drained from  Pilgrim  - ...` (out) / `-N GJ energy drained to  Curse  - ...` (in) | Sign and keyword carry direction. |
| Outgoing jam | ` Basilisk  jammed - Standup Variable Spectrum ECM II` | Only seen from a structure gunner. |
| Jam with full structure label | `You're jammed by  Astrahus [FRT]  [JN - Planet Fitness] - - Standup Variable Spectrum ECM I` | Ticker **and** name in brackets, double separator. |

The M1 corpus scan is designed to find these, which is the right process. The spec should not state what logs contain as fact before it runs.

### 1.5 Neut direction lives only in the colour code

Outgoing and incoming neut lines have identical text. Only the leading colour differs:

```
<color=0xff7fffff><b>180 GJ</b>... energy neutralized  Vexor Navy Issue  - Medium Energy Neutralizer II   (outgoing, 1,255 lines)
<color=0xffe57f7f><b>881 GJ</b>... energy neutralized Upgraded Avenger - Upgraded Avenger                 (incoming, 1,171 lines)
```

Plan §4.3 strips the pseudo-HTML before matching. That makes every neut undirected. Keep the first colour token as a field and let `patterns.py` use it.

### 1.6 ECM data is nearly nonexistent

About 500 jam lines exist across all 16k logs, mostly from NPCs (`Mercenary Crow`, `Blackout Handler`) and structures. Player ECM amounts to a few dozen lines (`You're jammed by  Kitsune  - Gravimetric ECM II`). Jam spans on the timeline and jam columns are designed around data that FFEW's own logs almost never produce. Keep them, but do not make them a milestone criterion.

## 2. Design choices that would give confidently wrong answers

### 2.1 Side guessing from one log cannot place YAGAS, and the AoE discount makes it worse

A single log is a star graph centred on the listener: every edge is listener ↔ X, except third-party tackle lines. In the sample:

| Interaction | Events |
|---|---|
| Listener smartbombs → YAGAS Sleipnirs | ~514 |
| YAGAS Sleipnirs smartbombs → listener | ~446 |
| Friendly events between listener and YAGAS | 0 (the only reps come from an unattributed Loki) |

With the plan's ×0.05 AoE weight that is 48 hostile vs 0 friendly. The confidence formula (margin ÷ total evidence) yields 1.0. YAGAS lands **hostile with full confidence**, the worst possible outcome.

Acceptance scenario 1 ("FFEW and YAGAS end up on the friendly side") and the M3 exit criterion are therefore unachievable from the analysis core alone. They silently depend on `FriendlyEntity` being pre-configured, which makes the test trivial.

Fix:

- Treat AoE-only interactions as **no hostile evidence at all** (groups that only ever smartbomb each other and never apply targeted weapons, ewar or tackle are not fighting).
- Consume the fleet notify lines from §1.3 as strong friendly edges.
- Make the honest single-log acceptance "YAGAS is Unknown until a second source (another log, killmails, FriendlyEntity) arrives".

### 2.2 Killmail signals are poisoned by the same friendly fire

zKill killmails for the fight (23 in the window, 21 in system 31001176). Corp 98754582 appears on every FFEW kill, so it is taken to be YAGAS.

| Loss, EVE time | Victim corp | Attackers | Own-side attackers |
|---|---|---|---|
| 20:28:45 Loki | FFEW | 41 | 8 FFEW, 9 YAGAS |
| 20:29:08 Sleipnir | YAGAS | 44 | 8 YAGAS, 8 FFEW |
| 20:30:55 Sleipnir | FFEW | 41 | 7 FFEW, 10 YAGAS |
| 20:35:04 Sleipnir | FFEW | 45 | 9 FFEW, 10 YAGAS |
| 20:35:13 Sleipnir | YAGAS | 50 | 9 YAGAS, 11 FFEW |

Plan §5.4 gives "+5 hostile victim vs attacker" and "+3 friendly for co-attackers". Applied to this data it marks FFEW hostile to itself and to YAGAS, and friendly to the enemy corps it co-attacked YAGAS losses with.

Fix: apply the same AoE rule to killmail attackers, using `weapon_type_id` (smartbomb group) and `damage_done` share; weight by damage share rather than per-attacker.

### 2.3 The zKill window misses the start of the fight

An FFEW Sabre died at 20:14:34. The listener's first PvP event is 20:19:25 and the plan's window opens at start − 2 min = 20:17:25, so that loss is excluded. A fight is wider than any one log. Let matched killmails extend the window and run one more pass.

### 2.4 Rebuild coalescing with QueueOnce drops work

Plan §4.2 relies on `QueueOnce` keyed on `fight_id` plus `countdown=15` to merge rebuilds. celery-once holds the lock until the task **finishes** (AA configures the `DjangoBackend`, default options). An upload that lands while a rebuild is running has its rebuild request discarded (graceful) or raises `AlreadyQueued` inside `process_log`. Either way the fight is never rebuilt with the new engagement.

Fix: a `needs_rebuild` flag (or version counter) set by `process_log` and re-checked at the end of `rebuild_fight`, which re-enqueues itself if the flag moved.

### 2.5 The 1-second skew assumption is unverified and load-bearing

Dedupe (§5.3) pairs events within 1 s at 1 s resolution. A 2 s clock difference between two members' PCs double-counts every shared event. Whether gamelog timestamps come from the server or the client clock is not established. Estimate the per-log-pair offset from the data by maximising matches over a small offset range (±10 s); two overlapping logs give this for free.

### 2.6 The PvP filter misclassifies in both directions

- "Player hull name ⇒ player" fires on NPC `Orthrus` (§1.4).
- The browser pre-filter requiring a `[TICK](Ship)` label skips logs where players appear as bare names (§1.4) and all pre-late-2022 logs (§3.7).

### 2.7 Several promised columns are not observable

- **Per-pilot tackle.** Under default labels tackle lines are ship type to ship type on both ends (`from Nighthawk to Sleipnir` ×22 in the sample, several Nighthawks and Sleipnirs present). "Points and scrams applied" per pilot is mostly unfillable.
- **Enemy reps given / neuts out / jams out** are visible only when they land on our logged pilots.
- **Hit %** is meaningless for smartbombs and missiles; needs an n/a state and should be limited to turret weapon groups.
- **"N sides"** from logs alone is friendly, hostile and unknown. Third parties need killmails.

The fight page should visibly distinguish observed cells from unobservable ones rather than relying on one coverage note.

## 3. Spec and plan gaps

### 3.1 Permissions disagree between the docs

- Spec: curators exclude logs. Plan §8: any contributor can run every curation action, including merging and splitting fights they did not create.
- Log deletion by the uploader silently undoes curation on affected fights.
- A sha256 duplicate is credited to the first uploader; the second uploader cannot see or delete it.
- Listener-based friendly seeding (§5.4 step 3) should apply only to Auth-owned characters; an `upload_any_log` user uploading a captured enemy log would seed the enemy as friendly.

### 3.2 Auto-merge is destructive and undefined

A new upload can merge two fights other people curated (§4.4). Nothing says what happens to the absorbed fight's title, notes, tags, `FightChange` history, `DiscordPost` rows and URL, nor to a fight emptied by log deletion. Keep stable IDs with a redirect table and define merge semantics field by field.

### 3.3 The listener's own ship is unknown from their own log

"You" lines never name the listener's hull. Only other logs, killmails, tackle `to you!` context or notify module names give it, and the sample listener reshipped at least twice (Porpoise for gas, Sleipnir for the fight). The plan needs an explicit rule and a `ParticipantShip` source field.

### 3.4 The lever for "Unknown Loki" is a client setting, not an algorithm

The `ShipType  [PilotName]` label format (§1.4) gives per-pilot rep, cap, neut and tackle attribution directly. Make that setting the headline of the help page and the first thing the fleet is asked to change. Parse it in M1 and test for it.

### 3.5 Install burden is higher than it needs to be

`eveuniverse_load_data map` and type category 11 (NPC entities) cost the admin many minutes. Systems can be fetched lazily with `get_or_create_esi`, as §6 already does for zKill systems. NPCs can be identified by exclusion (no ticker, not a known ship/drone/charge type) without loading thousands of entity types.

### 3.6 The performance target is optimistic

Several pure-Python passes over 250k events (timeline, per-pilot, targets, hit %, breakdowns) will not reliably stay under 2 s. numpy is a plain wheel and worth adding as a dependency.

### 3.7 Old logs are a mainstream case

6,338 of 16,217 corpus filenames (39%) lack the character ID suffix. Logs before late 2022 have no `[TICK](Ship)` labels at all (first seen 2022-10-08; still absent in a 2023-01-26 PvP log). The name-based listener fallback is the normal path, not an edge case, and the pre-filter must not require ticker labels.

### 3.8 Smaller items

- "FFEW" is hardcoded in the auto title of a public plugin; derive the friendly label from the Auth's main alliance or a setting.
- "No PvP, not stored" conflicts with "keep raw to re-parse" once the parser learns new PvP shapes.
- The supersede prefix check (§4.1) fails on a copy taken mid-write with a partial last line; compare up to the old file's last complete line.
- Ship-only participant keys embed the side (`ship:Loki@side`), so manual overrides on them break when the side guess changes.
- The help page should cover Mac and Linux log paths.
- `max_allowed_packet` note is fine, but the engagement store check (§5.1) should also cover a single pathological log rather than treating overflow as "always a bug".

## 4. Recommended changes before M0

1. **Model corp vs alliance correctly.** Tickers from logs are corp tickers. Add `GetCorporationsCorporationId` and `GetAlliancesAllianceId` (or eveuniverse `EveEntity`) to resolve alliance membership and tickers. Group by alliance for sides and titles.
2. **Widen parser scope** to `(None)`, `(notify)` and `(question)` lines for system, fleet, reship and clone-jump events. Keep the leading colour token on every combat line.
3. **Rewrite §5.4 and §6** around "AoE is never hostile evidence", fleet signals as friendly edges, and damage-share-weighted killmail attackers with the smartbomb discount.
4. **Replace QueueOnce coalescing** with a needs-rebuild flag checked at the end of `rebuild_fight`.
5. **Estimate clock offset per log pair** in dedupe instead of assuming ≤ 1 s.
6. **Rewrite acceptance scenario 1 and the M3 criterion** so they are achievable from a single log: FFEW friendly, the five enemy corps hostile, YAGAS Unknown; YAGAS friendly once killmails or a YAGAS log join.
7. **Reconcile permissions** (who can exclude, merge, split, delete) and define merge and deletion semantics.
8. **Mark observable vs unobservable metrics** in the spec and the UI; make the `ShipType [PilotName]` label setting the primary help-page recommendation.
9. **Drop the map and NPC category loads** from the install in favour of lazy lookups.
