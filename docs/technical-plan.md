# ffew-fightlog — Technical Plan (v1.1)

Revised 2026-10-26 after the [review](review-2026-10-26.md) and the [response to it](review-2026-10-26-response.md). The changes are:
- dropping django-eveuniverse in favour of a bundled type catalog
- a new parser classification
- parsing non-combat context lines
- corrected side-guessing rules
- per-log clock offsets
- celery-once settings that no longer drop rebuilds
- merge, deletion and attribution rules
- revised milestones

This plan implements the [product spec](product-spec.md). It covers the stack, the repo layout, the data model, the processing pipeline, the analysis algorithms, the UI and the milestones. The design was checked against several sources:
- Alliance Auth 5.5.0 (`master` @ 03f71076)
- the official [example plugin](https://github.com/AllianceAuth-Apps/allianceauth-example-plugin)
- aa-killtracker, as a reference app
- the local corpus of about 16k gamelogs, ESI and zKillboard

## 1. Constraints and decisions

| Topic | Decision | Why |
|---|---|---|
| Target platform | **Alliance Auth ≥ 5.5, Django 5.2, Python 3.10–3.14**, MariaDB in production, SQLite in tests | Matches AA's own `pyproject.toml`. FFEW's Auth runs the latest version. |
| Distribution | Public repo at `github.com/MrManiak/ffew-fightlog`. PyPI package `ffew-fightlog` (name is free). Python module and app label `fightlog`. **GPL-3.0**. The README and page footer carry the CCP copyright notice required by the EVE developer licence | Someone else administers FFEW's Auth, so installing has to be `pip install` plus the settings and migrations in the install doc. |
| Build | flit (`flit_core>=3.2,<4`), with version and description read from `fightlog/__init__.py` | Same as the example plugin and AA core. |
| Frontend | Django templates extending `allianceauth/base-bs5.html`, plus plain ES modules. Uses AA's bundled **Chart.js 4.4.1** (`bundles/chart-js.html`) and **DataTables 2.3.8** (`bundles/datatables-2-*-bs5.html`) | No Node build step, and the pages match AA's look and themes. |
| Language | English client logs only. Non-English logs are detected and rejected with a message | Decided with the user. Localized patterns can be added later. Only the message text is localized: damage labels and overview labels have the same format in every language. |
| Scale | Designed for **≤ 50 logs per fight**, roughly 250k events. Analysis runs in pure Python on packed arrays, with caching (§5) | Decided with the user. One aggregation pass over 250k events measured 0.14 s (Python 3.14), so numpy isn't needed. |
| EVE type data | A **bundled type catalog**, `fightlog/data/types.json.gz`, generated by `tools/build_type_catalog.py` from CCP's static data export (SDE) at release time. It maps names to `[type_id, group_id, category_id]` for ships, weapon and ewar modules, charges, drones, fighters, deployables, structures and NPC entities | Classification needs NPC names. ESI can't supply them: `/universe/ids/` resolves NPC names such as "Emergent Warden" to player characters. Loading them through django-eveuniverse costs the admin a long one-off load. A bundled catalog is deterministic and testable. |
| Solar systems | Copied on first use into a small `SolarSystem` table (system, constellation, region) from the bundled catalog, which carries every system from the SDE. ESI is the fallback for systems newer than the catalog. **No django-eveuniverse dependency** | A fight needs one or two systems, so there's no reason to load the whole map. |
| ESI | django-esi **OpenAPI** `ESIClientProvider` with an explicit list of operations, following AA core (`allianceauth/srp/providers.py`). Operations: `PostUniverseIds`, `PostUniverseNames`, `PostCharactersAffiliation`, `GetCorporationsCorporationId`, `GetAlliancesAllianceId`, `GetUniverseSystemsSystemId`, `GetUniverseConstellationsConstellationId`, `GetUniverseRegionsRegionId` | AA core no longer uses the old bravado client. The corporation and alliance calls supply tickers, since logs only carry corp tickers, and alliance tickers only in full labels. |
| Raw log storage | gzip-compressed `BinaryField` in the database. Django maps it to `LONGBLOB` on MariaDB. List and search queries use `.defer()` to skip the blob columns | AA's project template sets no `MEDIA_ROOT`, so this needs nothing extra from the admin. A typical log compresses to 50–100 KB. InnoDB stores blobs outside the main row, so metadata queries stay fast. |
| Event storage | **Packed columnar arrays in a blob per engagement**, not one database row per event | 250k rows per fight is wasteful, and the database never needs to filter on individual events. Search only uses the participant and fight tables. |
| Discord | Discord webhooks configured by the admin, posted with plain `requests` | AA's Discord service can't post to channels, and posts only happen manually, so we don't need a bot. |
| zKillboard | zKill `/api/` search endpoints, which **include the full ESI killmail** (`killmail_time`, `solar_system_id`, victim, attackers) plus `zkb` | No ESI killmail fetch is needed. R2Z2 is a live feed, and we only need lookups after the fact. |
| Tests | Django test runner via `runtests.py` and tox, the same as the example. `factory_boy` and `app_utils.testdata_factories`. HTTP mocked with `requests-mock`. Golden fixture: the five logs of the 2026-10-25 fight, anonymized, plus recorded zKill responses | `parser/` and `analysis/` are pure Python, so they also run on native Windows Python without the Docker stack. |

## 4. Pipeline

### 4.1 Upload (`views/upload.py`, `static/fightlog/js/upload.js`, `services/ingest.py`)

1. **Browser pre-filter.** The JS reads each file and applies these checks. It doesn't try to detect PvP: label formats vary too much (§4.3), so the server decides.
   - It reads the session start from the filename or the header, and keeps files in the chosen date range. The default is the last `FIGHTLOG_UPLOAD_DEFAULT_DAYS` (3) days.
   - It skips header-only files with no `Listener:` line. Every file without a character ID in its name is one of these.
   - It requires at least one `(combat)` line and English text markers.

   Accepted files are uploaded two at a time, one file per POST to `api/logs/`, with the CSRF token sent via AA's `fetchPost`.
2. **Server checks** in `ingest.accept_upload()`:
   - **Size:** reject files over `FIGHTLOG_MAX_UPLOAD_MB` (default 25).
   - **Encoding:** decode as `utf-8-sig`, falling back to `cp1252`. The raw bytes are kept as uploaded.
   - **Header:** parse the listener name and session start.
   - **Listener ID:** take the character ID from the filename (`YYYYMMDD_HHMMSS_<charid>.txt`). If the file was renamed, find the listener by name among the uploader's characters, and failing that resolve the name through ESI.
   - **Ownership:** `request.user.character_ownerships.filter(character__character_id=cid).exists()`, the same idiom as `allianceauth/srp/views.py`. If the user doesn't own the character, they need `upload_any_log`; otherwise the upload is rejected.
   - **Duplicates:**
     - An identical `sha256` adds a `CombatLogUpload` row and returns the existing log.
     - For the same `(listener, session_start)`, compare **raw bytes**:
       - Stored copy is a prefix of the new one: replace it. Its engagements are deleted and re-ingested.
       - New copy is a prefix of the stored one: no-op. The uploader is credited.
       - Anything else is a conflict, rejected with a message.
     - An append-only file copied mid-write is always a byte prefix of the later copy, so a partial last line is not a problem.
   - **Save:** create a `CombatLog(status=pending)` holding the gzipped raw file, plus its `CombatLogUpload` row, then `process_log.apply_async(args=[id], priority=4)`. The response returns `{id, status}`.
3. **Status.** The page polls `api/logs/<id>/` until the status is final, then shows one of:
   - *joined fight X*
   - *new fight*
   - *no PvP found*. The log stays hidden until `purge_after`, which is set to now + `FIGHTLOG_NO_PVP_RETENTION_DAYS` (30), so `reparse_all` can still find PvP in it after a parser upgrade.
   - *failed (reason)*. AA has no Celery result backend, so failures also go out through `notify(user, …, level="danger")`.

Logs are text files and can be forged. The ownership check catches honest mistakes, and the trust model assumes members aren't malicious. Every uploader is shown on the log, so each upload can be traced to the people who made it.

### 4.2 Celery tasks (`tasks.py`)

Every task uses `@shared_task` and `get_extension_logger`, passes only IDs as immutable signatures, and sets priorities as AA documents them.

| Task | Priority | Single-flight | Does |
|---|---|---|---|
| `process_log(log_id)` | 4 | `QueueOnce` keyed on `log_id` | Parse; save PvP engagements and the log's context events. Under a cache lock (`cache.lock("fightlog-clustering")` from django-redis), assign each engagement to a fight and bump the affected fights' `data_version`. Then `rebuild_fight.apply_async(countdown=15)` for each. |
| `rebuild_fight(fight_id)` | 5 | `QueueOnce`, `once={"keys": ["fight_id"], "graceful": True, "unlock_before_run": True}`, plus a non-blocking per-fight `cache.lock`. If the lock is held: `self.retry(countdown=10)` | Exits at once if `built_version == data_version`. Otherwise runs §5.2–5.5, sets `built_version` to the `data_version` it started from, and schedules `link_zkill` if the fight was never checked or the last check is stale. |
| `link_zkill(fight_id)` | 6 | `QueueOnce` keyed on `fight_id` | Runs §6. If it finds new killmails, it bumps `data_version` and queues `rebuild_fight`. Fights less than 24h old get re-checked at +1h, +6h and +24h, because zKill withholds killmails younger than 5 minutes and pilots post kills late. |
| `post_fight_to_discord(post_id)` | 3 | `QueueOnce` keyed on `post_id` | Runs §7. On a 429 it retries with `eta=retry_at`. |
| `reparse_all()` | 8 | `QueueOnce` | Triggered from the admin or `fightlog_reparse` after a parser upgrade. Re-parses every log whose `parser_version` is older than the current one, including `no_pvp` logs still within retention. |
| `purge_expired_logs()` | 8 | `QueueOnce` | Daily. Deletes `no_pvp` logs past `purge_after`. Scheduled through `CELERYBEAT_SCHEDULE`; `install.md` gives the entry, with `apply_offset: True`. |

**Why the `rebuild_fight` settings.** By default, celery-once holds its lock from enqueue until the task *finishes*. So with default options:
- any upload that lands during a rebuild is silently dropped
- a rebuild can't even re-queue itself at the end, because its own lock is still held

`unlock_before_run` fixes this. Uploads during the 15-second countdown merge into the queued rebuild, and an upload during a run queues exactly one follow-up. The mutex keeps two rebuilds of one fight from running at the same time, and the version check makes redundant runs cheap.

### 4.3 Parser (`parser/`)

**Reading**
- Keep the leading `<color=0x…>` token of every line as a field before stripping markup. Neut direction depends on it: outgoing is `0xff7fffff`, incoming `0xffe57f7f`, with identical text.
- Strip markup *before* matching text, because markup splits tokens (`to <b>…</b>you!`).
- Decode HTML entities *after* stripping tags. Labels write angle brackets as `&lt;` and `&gt;` (`Loki &lt;SPORK&gt;[SLAPD] BillyBulb`), so decoding first would let the tag stripper eat the alliance ticker.
- Never collapse whitespace inside labels. Tickers can contain spaces (`[J  H]`, `[BP RU]`).
- Keep `showinfo:<typeID>//<itemID>` targets. Fleet lines carry exact character IDs this way.
- `(combat)` lines become events. `(None)`, `(notify)` and `(question)` lines become context events.
- Timestamps are EVE time (UTC) at 1-second precision, stored as epoch seconds. Original line numbers are kept for drill-down.

**`Event`:** `t`, `kind`, `src: Actor`, `tgt: Actor`, `module`, `amount`, `quality`, `flags`, `line_no`.
- Kinds: `DAMAGE`, `MISS`, `REP_SHIELD`, `REP_ARMOR`, `REP_HULL`, `CAP_TRANSFER`, `NEUT`, `NOS`, `JAM`, `SCRAM`, `DISRUPT`, plus `EWAR_OTHER(subtype)` for whatever else the corpus turns up.
- Tackle direction:
  - `from you to X`: the source is the listener.
  - `from X to you!`: the target is the listener.
  - `from X to Y`: `OBSERVED`. Neither end is the listener.
- Damage quality: Wrecks, Smashes, Penetrates, Hits, Glances Off, Grazes.
- `flags`: `AOE` (smartbombs and bombs, from the catalog group of the module), `DRONE`, `OBSERVED`, `NON_SHIP_TARGET`.

**`ContextEvent`:**
- `FLEET_INVITE` and `FLEET_JOIN`, with the character ID from showinfo
- `FLEET_WARP` and `REGROUP`, with a name
- `SYSTEM`, from a jump or undock
- `RESHIP`, `CLONE_JUMP`
- `KILL_NOTICE`, with the victim name
- `WSPACE_HINT`: `Local spatial phenomena…`, or `spatial disturbances caused by the wormhole`

M1 records the exact fleet-leave lines. Until then, a fleet membership lasts until the next fleet join or the end of the session.

**Labels.** There are two kinds:
- **Damage and miss lines** always use `Pilot[CORP](Ship)`, whatever the client's settings.
  - Structures look like `JN - The Event Horizon[EVEHD](Astrahus)`: names can contain " - ", and lines can repeat the weapon/quality segment and end in `(N deflected)`.
  - Drones and fighters can also appear as `X belonging to Pilot`.
- **All other lines** (reps, cap, neuts, nos, jams, tackle) use the listener's **overview ship label**. Its fields (ship type, alliance ticker, corp ticker, pilot, ship name), their order and their brackets are configurable. The label is stored per EVE account, and an overview profile can replace it. So `labels.py` learns a **template for each log**:
  1. Take the pilots that the fight's damage lines identify exactly: name, corp ticker and ship.
  2. Find those pilots in the log's other lines, and work out which field sits where and in which brackets.
  3. Try the known templates first: ship type only; `Ship [Pilot]`; the stock `Ship <ALLIANCE>[CORP] Pilot`; the full `Ship Pilot (corp) [alliance] - "ship name"`.
  4. Store the result in `CombatLog.label_template`. If labels stop matching mid-session (the player switched overview profile), learn again from that point.
- **Template details:**
  - Drones put their own name in the pilot slot (`Acolyte II [BCAUS] [KS88] [Acolyte II] -`, `Medium Armor Maintenance Bot I [Medium Armor Maintenance Bot I]`).
  - Structures put their name there too (`Astrahus [FRT] [JN - Planet Fitness]`).
  - There is a double-separator variant, `Ship [Pilot] - - Module`.
- **`you` / `Your group of …`** means the listener.
- **NPCs get no label.** They appear as bare names.

**Classification** (`classify.py`), first match wins:
1. **Labelled actors are player-owned.**
   - In damage lines, the `(Ship)` part, looked up in the catalog, says whether it is a ship, drone, charge (a missile in flight), deployable or structure.
   - In other lines, the learned template gives the same fields, and a pilot slot holding a drone type means a drone.
2. **A bare name seen labelled anywhere in the same fight** is that player.
3. **Incoming damage with no weapon segment** is an NPC. The corpus has 286,587 such lines, and labelled actors never lack a weapon.
4. **A bare name that is an NPC type in the catalog** is an NPC. This catches NPC missile boats such as Gist Cherubim, whose lines do carry a weapon.
5. **A bare name that is only a player hull, in rep, cap, neut, jam or tackle lines,** is a ship-type-only player actor. A name that is both an NPC type and a hull (e.g. "Orthrus") is ambiguous, and never counts as PvP evidence on its own.
6. **Anything else** is unknown, and doesn't count as PvP evidence.

ESI name lookups are **never** used to classify bare names: "Emergent Warden", "Starving Damavik" and "Upgraded Avenger" are NPCs and also real player characters.

**PvP filter.** An engagement needs at least `FIGHTLOG_MIN_PVP_EVENTS` events involving a player-owned actor or a ship-type-only player actor.

**Formats come from the corpus first.** Milestone 1 runs `tools/corpus_scan.py` over all ~16k local logs (2022-10 onwards), combat *and* context lines. It records every line "shape" with counts in `docs/log-formats.md`, with names anonymized. Each shape gets a pattern and an anonymized fixture. Lines that match no pattern become parse warnings on the log, never crashes. `parser_version` is bumped whenever a pattern changes.

### 4.4 Engagements, clustering, merging and deletion (`analysis/engagements.py`, `services/clustering.py`, `services/curation.py`)

- **Engagements.** A log's PvP events are sorted and split wherever the gap exceeds `FIGHTLOG_ENGAGEMENT_GAP_SECONDS` (300). Engagements with fewer than `FIGHTLOG_MIN_PVP_EVENTS` (5) PvP events are dropped.
- **Assignment.** The candidate fights for an engagement are those whose `[start, end]` overlaps it, allowing ± `FIGHTLOG_MERGE_TOLERANCE_SECONDS` (120).
  - A candidate qualifies when it shares at least one pilot key with the engagement, or when the engagement's listener appears in the fight (or the other way round).
  - No qualifying fight: create a new fight.
  - One: join it.
  - Several: merge them, unless any of them is curated (`is_curated`, meaning it has at least one `FightChange`). In that case the engagement joins the curated fight it shares the most participants with.
- **Merging**, whether automatic or by hand:
  - The surviving fight is the curated one, otherwise the one with more logs, otherwise the older one.
  - The title is the manual title if there is one, otherwise regenerated.
  - Notes are concatenated, with a separator naming the source fight. Tags are the union of both.
  - `FightChange`, `DiscordPost` and the side and attribution overrides move to the surviving fight. On a conflict the surviving fight's value wins, and the conflict is logged.
  - A `FightRedirect` is written for the absorbed ID.
  - A manual merge needs edit rights on both fights.
- **Splitting** a fight at timestamp T moves the engagements after T to a new fight. Engagements that span T are split in two by slicing their stores. Both fights get a `FightChange`, which makes them curated, so automatic clustering won't merge them again.
- **Deleting a log** is allowed for any of its uploaders, the owner of its listener character, or a curator.
  - It removes the log's engagements.
  - Each affected fight gets a `delete_log` `FightChange`.
  - A fight left with no engagements is deleted if it isn't curated and has no Discord posts. Otherwise it is kept as an empty record.

## 5. Analysis

### 5.1 Packed event store (`analysis/store.py`)

- **Format:** typed `array` columns for `t`, `kind`, `src`, `tgt`, `module`, `amount`, `quality`, `flags` and `line_no` (fight chunks also carry `log_id` and `dup_group`). `src`, `tgt` and `module` are indexes into string and actor tables. Encoded as `zlib(header JSON + array.tobytes())`. Context events are few, so they stay in `CombatLog.context`.
- **Size:** 250k events × 11 int32 columns is about 11 MB uncompressed and a few MB compressed, and it decodes in milliseconds.
- **Cache:** each process keeps the 4 most recently decoded stores in an LRU keyed by `(fight_id, built_version)`.
- **Row size:**
  - Fight stores are written as `FightDataChunk` rows of at most 100k events each, around 4 MB uncompressed at worst. A 50-log fight is about 3 chunks.
  - `store.encode()` refuses to write a blob over `FIGHTLOG_MAX_BLOB_BYTES` (default 8 MB, half the packet limit). Engagement stores get the same check.
  - A single log can't reach the limit. The largest real log is 8.8 MB raw, the upload cap is 25 MB, and at about 36 bytes per event against about 235 bytes per raw line, even a capped log stays under 4 MB *uncompressed*.
  - So if the check fires, it is a bug, not a normal situation. It shows up as a failed rebuild, never as a database error in the middle of a write.

### 5.2 Identity resolution (`services/resolve.py`, `analysis/hulls.py`, `analysis/attribution.py`)

- **Names from labels:** looked up in batches through `PostUniverseIds` (≤ 500 names per call), then `PostCharactersAffiliation` (≤ 1000 IDs per call), and cached in `ResolvedName`. Corporation and alliance tickers and names come from `GetCorporationsCorporationId` and `GetAlliancesAllianceId`, cached in `Corporation` and `Alliance`. Fleet lines give character IDs directly.
- **The provider** lives in `fightlog/providers.py`:
  ```python
  esi = ESIClientProvider(ua_appname="ffew-fightlog", ua_version=__version__,
      ua_url="https://github.com/MrManiak/ffew-fightlog",
      compatibility_date="2026-05-19",   # match allianceauth.eveonline; re-check on upgrades
      operations=["PostUniverseIds", "PostUniverseNames", "PostCharactersAffiliation",
                  "GetCorporationsCorporationId", "GetAlliancesAllianceId",
                  "GetUniverseSystemsSystemId", "GetUniverseConstellationsConstellationId",
                  "GetUniverseRegionsRegionId"])
  ```
- **Tickers.** The `[CORP]` in damage labels is the corporation ticker at fight time. Alliance tickers come from overview labels when the listener's label includes them (the stock label does), otherwise from affiliation lookups. ESI only returns current affiliations, so display and grouping prefer data from the time of the fight:
  1. tickers from the log
  2. killmail affiliations
  3. current ESI affiliations
- **Hull timelines (`hulls.py`).** A pilot's hull at time t comes from:
  - other logs' labels (`to Misterma Niak[FFEW](Sleipnir)`)
  - killmails (attacker or victim `ship_type_id`)
  - weakly, the pilot's own module names

  Reship and clone-jump context events end an interval, and each `ParticipantShip` row records its source. In the reference fight, other logs give every listener's hull.
- **Ship-type-only actors (`attribution.py`)**, in order:
  1. **Peer-log match.** When the actor's counterpart uploaded a log, the matching event in that log names them: same kind, amount and module, within ±2 s after offsets (§5.3).
  2. **Elimination.** The candidates are participants on the implied side flying that hull at the time. Drop any candidate whose log covers that moment but has no matching outgoing event. If exactly one remains, attribute the actor to them (`elimination`).
  3. **Otherwise** the actor stays as *Unknown Loki (friendly)*, keyed `s:<log>:<polarity>:<raw label>`.
  4. **An `AttributionOverride` wins** over all of these.

  Example: none of the five 2026-10-25 logs has an outgoing rep, so PaidProgramming, the only logged Loki, is eliminated for the reps Misterma Niak received.

### 5.3 Clock offsets and cross-log deduplication (`analysis/offsets.py`, `analysis/dedupe.py`)

- **Offsets.**
  - For each pair of logs that share events, count matches at every shift within ±`FIGHTLOG_CLOCK_OFFSET_SEARCH_SECONDS` (10). The best shift is the pair's offset.
  - Solve per-log offsets relative to the log with the most matches. Sanity-check them against killmails: no hit should be logged more than 2 s after its victim's killmail time.
  - Offsets above 2 s are flagged in the log panel.
  - Measured on the five same-PC logs: 788 of 805 matches at 0 s, the rest within ±2 s.
- **Matching.** After applying offsets, match events by kind, amount, module and compatible identities, within ±`FIGHTLOG_DEDUPE_TOLERANCE_SECONDS` (2), pairing them greedily in time order. A ship-type-only "Loki" is compatible with pilot A if A flew a Loki at that time.
- **Observed events.** Third-party tackle seen by several logs is deduplicated the same way. An observed `X → Ship` in log A that matches `X → you!` in log B at the same second names its target as B's listener. Example: at 20:26:30, Teamsesh's log shows `Nighthawk → Sleipnir` while Undocks with PLEX's log shows `Nighthawk → you!`.
- **Result.** Each matched set gets a shared `dup_group` ID in `FightData`. Aggregation counts a group once if **any** of its logs is in the active set. That keeps totals right however the viewer toggles logs.

### 5.4 Side guessing (`analysis/sides.py`)

1. **Group nodes:** participants by alliance (from affiliations, or from alliance tickers in overview labels), falling back to corporation, then the individual. Manual assignments pin a node.
2. **Evidence.** The weights are constants in `sides.py`, tuned against the golden fixtures.
   - **Hostile, from logs:**
     - targeted damage, neuts, nos, jams and tackle: +1 per event
     - AoE damage (smartbombs, bombs): **0**
   - **Friendly, from logs:**
     - reps and cap transfers: +2 per event
     - fleet membership during the fight (invite or join, fleet warp, regroup): +5 per relation, but only while the membership is valid. A fleet joined after the fight doesn't count.
   - **Killmails:**
     - An attacker is **AoE-suspect** if its `weapon_type_id` equals its own `ship_type_id`, if its weapon is a smartbomb or bomb type, or if every log-observed shot from that pilot was AoE.
     - AoE-suspect attackers are dropped. In the reference fight, 201 of the 264 FFEW/YAGAS attacker entries record the hull as their weapon, against 15 of 245 enemy entries.
     - For the remaining attackers: the victim's group is hostile to each attacker's group, weighted by that attacker's damage share. Attackers of the same victim are friendly to each other, weighted by the smaller share.
3. **Seeds:** groups containing characters owned by any Auth user, plus `FriendlyEntity` entries, go to the friendly side. Listeners that no Auth user owns seed nothing. If a fight has no seed at all, the most active group with enough hostile evidence anchors side 1, the friendly side stays empty, and the title and default view use the two largest sides.
4. **Greedy signed clustering.**
   - Take groups in descending order of interaction weight.
   - Assign each one to the side with the best score (friendly weight to the side minus hostile weight to it), if that score is positive.
   - If every score is zero or negative and the group has enough hostile evidence, start a new side. If the group has too little evidence overall, put it in **Unknown**.
   - Then make two more passes so the result settles.
   - Extra hostile sides (third parties) need killmail evidence between hostile groups.
5. **Hints.** A group gets `hint=aoe_mutual_only` (shown as "likely friendly") but stays Unknown when, during an engagement where our pilots used targeted weapons on others:
   - it exchanged AoE hits with our pilots in both directions
   - it had zero targeted interactions with our pilots
6. **Confidence** is the winning score's margin divided by the group's total evidence. Groups with confidence below `FIGHTLOG_SIDE_MIN_CONFIDENCE` go to Unknown.
7. **Existing sides:** map the new sides onto the existing `Side` rows by largest overlap. Manual assignments always win.

**Validation.** These rules were simulated on the reference fight, at corporation level, using the five logs plus 22 killmails:

| Rules | Friendly | Hostile | Unknown |
|---|---|---|---|
| The v1 weights (AoE ×0.05, co-attackers +3) | FFEW, YAGAS and 12 enemy corps | 2 corps | — |
| The rules above | FFEW, YAGAS | all 12 enemy corps | NPE. |

### 5.5 Aggregation (`analysis/aggregate.py`)

Inputs:
- the fight store
- the participant→side map
- the active log set (the curated default, or `?logs=` from the viewer)
- the perspective: a side, a pilot or a log
- the bucket size: 5, 10, 30 or 60 s

Outputs:
- **Timeline:** per bucket, in and out values for damage, reps (by type), neut/nos GJ, jams and tackle, plus friendly fire as its own series. "Out" means the source is in the perspective. "In" means the target is in the perspective. Core and related killmail markers are included.
- **Per-pilot table:**
  - damage dealt and taken, and friendly fire dealt
  - hit % and the hit-quality histogram
  - reps given and received (shield, armor, hull)
  - cap given and received
  - neut and nos GJ, out and in
  - jams out and in
  - scrams and disruptions applied and received
  - `has_log`
  - row breakdowns by weapon and by target
- **Targets table:** for each pilot that took damage, the time from first hit to the kill (from the killmail) or the last hit, damage taken, number of shooters, and reps received in that window.
- **Drill-down:** the events for a time range, filtered by perspective and kind, paginated, each with its source log and line number.
- **Cell states:**
  - *complete*: the pilot has an active log
  - *partial*: only events that touched active logs
  - *n/a*: the metric doesn't apply
  - *unattributed*: ship-type-only events not credited to anyone
- **Metric rules:**
  - Damage to drones, charges and deployables is kept out of pilot totals unless `include_non_ships=1` is passed.
  - Friendly fire (source and target on the same side) is kept out of damage dealt.
  - Hit % is hits ÷ (hits + misses), computed per shooter and weapon group, and only for weapon groups that can miss: turrets, drones and fighters. Everything else is *n/a*. In the corpus, missiles (210,072 lines) and smartbombs (109,049 lines) always "Hit".
- **Caching:** the default view is precomputed into `Fight.summary` during rebuild. Any other view is cached in the Django cache (Redis) under `fightlog:agg:{fight}:{built_version}:{sha1(logset)}:{perspective}:{bucket}` for 24 h. A new `built_version` invalidates all of them.

## 6. zKillboard linking (`services/zkb.py`)

1. **Seed entities:** friendly alliance and corporation IDs (from Auth members and `FriendlyEntity`), plus up to `FIGHTLOG_ZKB_MAX_ENTITY_QUERIES` (8) of the most active resolved participants.
2. **Query:**
   - For fights less than 7 days old: `https://zkillboard.com/api/{entity}ID/{id}/pastSeconds/{s}/`, where `s` is the fight's age plus margin, rounded up to a multiple of 3600.
   - Older fights: `/{entity}ID/{id}/year/{Y}/month/{M}/page/{n}/`.
   - Results are newest-first, 200 per page, so paging stops as soon as killmails are older than the window start minus 15 minutes. The entity modifier always comes first in the path.
3. **Core kills:** killmails in [first log event − 2 min, last log event + 5 min] that involve at least two fight participants.
4. **Expansion:** for up to `FIGHTLOG_ZKB_EXPANSION_ROUNDS` (2) rounds, add killmails within `FIGHTLOG_ZKB_EXPANSION_MINUTES` (15) of the current window that share at least two participants. These kills, and core kills in other systems, have role `related`.
   - Example: Kmcpilot's Sabre (20:14:34, J-space system 31002133, three shared pilots) joins as related.
   - Example: the 20:06:46 Omen Navy Issue kill shares only its victim, so it doesn't join.
5. **System:**
   - The most common system among core kills. If it's new, run one more `solarSystemID/{sys}/…` query to pick up kills nobody in the seed list was on, then fetch the system into `SolarSystem`.
   - **Source order:** manual > zkb > log > wspace_unknown.
   - **The log rule:** use the latest `SYSTEM` context event before the engagement, but only if no `WSPACE_HINT` lies between it and the end of the engagement.
   - **Otherwise,** when w-space hints are present, the system is "J-space, system unknown". Wormhole jumps are never logged.
   - Example: the sample log's only system line is an undock in Nema at 21:00:46, after the fight. The fight itself was in J-space system 31001176.
6. **Save:** upsert `Killmail` rows, computing each attacker's `aoe_suspect` flag, and link them to the fight with their role.
7. **Etiquette:**
   - User-Agent: `ffew-fightlog/<ver> (+https://github.com/MrManiak/ffew-fightlog)`, plus `Accept-Encoding: gzip` and a trailing slash on every path.
   - At least `FIGHTLOG_ZKB_REQUEST_DELAY_MS` (1000) between requests across all workers, coordinated through a cache key in the style of `killtracker/core/zkb.py`.
   - A 429 sets `retry_at` from `Retry-After`, and the task retries then.

## 7. Discord (`services/discord.py`)

- **UI:** users with `post_to_discord` see a button, pick an enabled `DiscordWebhook`, and confirm. If the fight was posted before, the dialog warns about it.
- **Message:** a single embed with:
  - title and link to the fight
  - EVE time window and system
  - pilots and losses per side
  - ISK destroyed
  - top damage and top logi
  - number of logs
  - footer "ffew-fightlog"
- **Delivery:** a POST to `url?wait=true` with `requests`. The returned message ID is saved on `DiscordPost`. A 429 reads `retry_after` and retries. Any other error is saved and reported to the user with `notify()`.
- **After a merge:** links in old posts keep working through `FightRedirect`.

- **Tests:** `python runtests.py fightlog` with `DJANGO_SETTINGS_MODULE=testauth.settings_aa5.local` runs on native Windows Python, against a local Redis. `e2e/` drives the dev stack over HTTP and in Chromium (Playwright), including a timed synthetic 50-log fight.
- **Real logs:** `tools/corpus_scan.py <Gamelogs folder>` runs locally. Its output is untracked, because real logs contain other players' names.

## 12. Risks and open questions

Answered so far (details in the [response](review-2026-10-26-response.md)):
- The `[TICK]` in damage labels is the corp ticker. Alliance tickers appear only in overview labels that include them, and the stock label does.
- Rep, cap, neut, jam and tackle lines name actors with the listener's overview ship label. It is set per EVE account and can come from an overview profile. Damage lines use `Pilot[CORP](Ship)` on every client, and only the message text is localized. This comes from the user, based on the client's code.
- `from X to Y` tackle lines are third-party. Tackle on the listener reads `to you!`.
- The formats of outgoing ECM, cap transfers and nos are known.
- Wormhole jumps are never logged.

Still open:
- **Bare player names in damage lines.** One player (ThinkBigShiite) appears without `[CORP](Ship)` in 2025 Sleeper-site logs. The cause is unknown. The classification rules (§4.3) handle it.
- **Clocks across different PCs.** Per-log offsets handle skew either way. Watch how often offsets get flagged.
- **Killmails recording the hull as the weapon.** This is confirmed for smartbombers. It also shows up for 15 of 245 enemy attacker entries in the reference fight, so dropping AoE-suspect attackers loses a little evidence. Revisit with more fights.
- **Other area weapons.** Bombs, doomsdays, burst projectors and vorton chains are treated as AoE once M1 confirms their catalog groups.
- **NPC names missing from the catalog** (new content between releases). These fall back to the line-shape rules, and the catalog is refreshed every release.
